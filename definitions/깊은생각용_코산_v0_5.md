# 깊은생각용 코산 v0.5

> 메타코산 v0.2의 Q1~Q8에 답하려 한 결과. **세 번째 도메인이다.**
> **경고: Q1에서 STOP 났다.** 우회하지 않고 그대로 적었다. §STOP 참조.
> 그 STOP이 메타의 버그를 드러냈고, 이 문서의 절반은 그것을 다룬다.

**v0.1 → v0.2 변경점: 실제로 한 판 굴려보고 드러난 것들을 반영.**
v0.1로 굴렸더니 **시뮬레이터(AI)가 앵커링에 걸렸다.**
축을 세 개 열어놓고 **한 축만 굴렸다.** 그런데 v0.1의 PASS 조건을 전부 통과했다.
→ **열기만 하고 안 굴려도 통과하는 구멍이 있었다.** (§v0.2 핵심 수정)

또한 v0.1은 코산이 잡아내는 것을 두 종류로만 봤다. 굴려보니 **셋이었다.** (§세 가지 검출)

**v0.2 → v0.3 변경점: 렌더링 규율을 추가했다.**
실제로 이 코산으로 논문을 분석하고 렌더링했더니, **렌더링 AI가 `??` 자리를 그럴듯하게 메꿨다.**
O5 에 `forks=[F15,F16]` 만 있고 둘의 관계가 없었는데(암묵적 공백),
렌더링이 "초기엔 F15, 나중엔 F16" 이라는 **소스에 없는 시간 순서를 지어냈다.**
→ **렌더링에 규율이 없어서 채우는 걸 선택했다.** (§렌더링 규율)
**v0.3 → v0.4 변경점: 렌더링 참조망 격리를 추가했다.**
v0.3 렌더링이 "F1 에 의존한다" 를 **"F1 이 먼저 확립되어야 성립한다"** 로 옮겼다.
`depends [F1]` 에는 순서가 없다. F1.cosan 에도 순서가 없다.
그 "먼저/선행" 은 **참조망 밖**(자동 로드된 메모리 · 게임 상식)에서 새어 든 것이다.
→ **렌더링은 대상 노드 + 참조망만 봐야 한다.** (§렌더링 규율 4)
→ 그리고 `depends` / `->` 를 **시간 순서로 변환하지 마라.** (§규율 5)

**v0.4 → v0.5 변경점: 앵커링 검출을 바로잡고, 세 열린문제를 사람 몫으로 재분류했다.**
v0.4 는 앵커링을 **steps 개수(한 축이 과반)** 로 기계 판정하려 했다. 그건 보조 신호일 뿐이다.
진짜 앵커링 탈출은 **사람이 "이 축으로 생각하면?" 하고 새 축을 던지고,
코산이 그것을 독립 함수로 굴려 기존 옆에 쌓는 것**이다. (§앵커링 탈출)
그리고 v0.4 의 "아직 모르는 것" 세 개(?? axis 찾기 / depth 멈춤 / steps 기준)는
**AI 가 풀 난제가 아니라 사람이 하는 판단**이었다. 코산의 일은 찾아 채우는 게 아니라
**쏠림과 빈 곳을 보이게 하는 것**이다. (§코산이 하는 일 / 사람이 하는 일)

```
깊은생각용 코산 정의  →  <문제>.코산  →  굴린다  →  trace  →  (원하면) 렌더링 = 글
```

## ★★ 산출물 형식 — 이것을 먼저 지켜라 (모든 코산 공통)

**이 세 가지는 도메인과 무관하게 고정이다. 어기면 코산이 아니다.**

### 1. 확장자는 `.cosan` 이다

```
✗  KOSAN.md,  *.kosan,  *.md,  *.txt
✓  *.cosan
```

**영문 표기는 `COSAN` 이다.** (**co**de + **san**mun(산문) → co-san / 코산 — 산문이라는 매체를 코딩화한다는 뜻. sanmun = Korean for "prose".) `kosan` 이 아니다.
`kosan` 이 아니다. 개별 코산 객체는 `.cosan` 파일로,
이 프로젝트의 문법·구조·지도는 최상위 `COSAN.md` 에 둔다.

### 2. 코산은 파일/폴더 구조로 만든다 ★★ 한 파일에 다 넣지 마라

**코산은 "코딩된 산문"이다. 코드처럼 ★ 파일과 폴더로 나눈다.**

```
✗  전부 한 파일(.md, .txt)에 텍스트로 쓴다
    → ★ 그 순간 산문으로 돌아간다.  이 방법의 존재 이유가 사라진다.
    → 한 파일이면 참조가 안 되고,  부분만 열 수 없고,  스케일이 안 된다.

✓  객체마다 파일 하나.  종류마다 폴더 하나.
    → 코드베이스처럼.
    → 필요한 파일만 연다.  나머지는 안 읽는다.  (작은 모델·긴 작업에 결정적)
```

**한 객체 = 한 `.cosan` 파일. 한 종류 = 한 폴더.**
파일 안에서 다른 객체는 **코드 이름으로 참조**한다 (예: `home = W_APT_601`).
참조가 관계를 붙들기 때문에, 파일을 나눠도 안 흩어진다.

### 3. 코드 이름은 영문. 값만 자국어.

```
✓  char C_AJUMMA { name = "박순자" }      ← 손잡이는 영문,  값은 따옴표 안 자국어
✗  캐릭터 아줌마 { 이름 = 박순자 }
```

**영문 코드 이름이 유일한 불변(주소)이다.** 값(이름 등)은 바뀌어도 참조가 안 끊긴다.

## 0. 이 도메인의 대전제

```
깊은 생각 = ??                    ★ 아직 못 정했다.  아래 참조.
목적      = 답을 얻는 것이 아니다.  ★ 답이 어디에 있는지를 아는 것.
글        = 렌더링 산출물.  소스에 칸이 없다.
```

### 왜 대전제를 못 쓰는가

소설과 토론은 대전제가 바로 나왔다.

```
소설  =  인물이 원칙을 지키거나 버리는 결정의 연쇄
토론  =  주장이 공격받고 살아남거나 죽는 연쇄
```

**둘 다 "무엇이 무너지는가"로 정의된다.** 그래서 굴릴 수 있었다.

깊은 생각은 그렇게 안 된다.

```
✗  깊은 생각 = 주장이 검증되는 연쇄       ← 그건 토론이다
✗  깊은 생각 = 답에 도달하는 연쇄         ← 답이 있는 줄 알면 이미 생각한 것이다
✗  깊은 생각 = 결정의 연쇄               ← ★ 여기서 막힌다
```

**깊은 생각의 대부분은 결정이 아니다. 결정을 미루는 것이다.**

## v0.2 핵심 수정 ★ (한 판 굴려보고 나온 것)

### 수정 1. 열기만 하고 안 굴려도 통과했다 ★★ 최대의 구멍

**v0.1의 PASS 조건:**
```
□ 같은 from 에서 axis 가 2개 이상 열렸는가     ← 이것만 봤다
```

**실제로 굴렸더니:**
```
O1(차별화_대상)   스텝 8개 소모.  갈래 전부 굴림.  축 무효화까지 감.
O2(중독의_출처)   스텝 0개.       갈래 3개 열어놓고 방치.     ← ★
O3(실패_모드)     스텝 2개.
```

**축은 세 개 열었다. PASS 조건을 통과했다. 그런데 한 축만 팠다.**

`open` 은 값싸다. AI는 축을 얼마든지 열 수 있다.
**그리고 열어놓고 안 굴린다.** 열었다는 사실이 알리바이가 된다.

```
✗  □ axis 가 2개 이상 열렸는가          ← 열기만 검사.  통과 가능.
✓  □ axis 가 2개 이상 실제로 굴려졌는가  ← 스텝 소모를 센다
✓  □ 한 axis 가 전체 스텝의 과반을 먹지 않았는가
```

**발산은 여는 것이 아니라 굴리는 것이다.**
열기만 한 축은 갈래가 아니라 **장식**이다. (소설의 "clash 안 걸린 원칙"과 같다)

### 수정 2. 편향은 개별 검사로 안 잡힌다 ★

굴린 판에서 **모든 개별 노드가 정상이었다.**

```
K1  ground 있음.  정상.
K2  ground 있음.  정상.
C3  근거 있음.    정상.
```

위반이 하나도 없는데 **전체가 기울어 있었다.**

**편향은 잘못한 것이 아니라 잘한 것들의 분포다.**
그래서 노드 검사로는 원리적으로 안 잡힌다. **세어서 비교해야 잡힌다.**

```
빈틈    개별 노드에 칸이 비었다          →  노드 검사로 잡힌다
창작    개별 노드를 근거 없이 채웠다      →  노드 검사로 잡힌다
편향    ★ 노드는 다 정상인데 분포가 기울었다  →  ★ 집계 검사로만 잡힌다
```

→ **PASS 에 집계 검사를 추가한다.** (§Q6)

### 수정 3. 통과 조건이 앞 스텝을 소급 무효화한다

굴리다가 통과 조건을 확정했더니:

```
PASS = "내가 만들고 싶은 재미"
   → ⚠ K1.ground = "시장에서 다 망했다"
   → 시장 근거.  PASS 와 무관.
   → K1 무효.  죽었던 갈래가 ?? 로 복구.
```

**통과 조건은 나중에 넣어도 앞으로 전파된다.**
그러므로 통과 조건 확정도 **하나의 스텝**이고, cascade 를 발동시킨다.

```
✓  step  set_pass(<조건>)
         cascade  모든 kill.ground 를 PASS 기준으로 재검사
                  기준과 무관한 ground 로 죽은 것 → ?? 로 복구
```

**v0.1은 통과 조건을 코산 밖에 뒀다. 안에 넣어야 한다.**

## 세 가지 검출 ★ v0.2 신규

코산이 잡아내는 것은 셋이다. **셋의 경로가 다르다.**

```
① 빈틈    안 채운 칸
          →  훑으면 보인다.  구조가 그냥 알려준다.
          →  ground 없는 kill,  회수 안 된 leaves,  ?? 로 남은 값
          →  ★ 산문에는 존재조차 안 남는다.  안 쓴 건 안 보인다.

② 문제점  모순.  왔던 길이 틀렸다.
          →  굴려야 나온다.  상태를 통과시켜야 드러난다.
          →  전제가 죽고, cascade 가 돌고, 앞 스텝이 무효가 된다
          →  ★ 메모는 못 한다.  메모는 안 굴러가니까.

③ 편향    안 판 축.  기울어진 분포.
          →  세야 나온다.  집계해야 드러난다.
          →  축이 이름을 갖고 있어야만 셀 수 있다
          →  ★ 산문에는 축이 없다.  그래서 축이 하나뿐이라는 것조차 안 보인다.
```

**셋의 쓸모도 다르다:**

```
빈틈    →  어디를 더 볼지 알려준다      →  다양성
문제점  →  왔던 길이 틀렸다고 알려준다   →  왕복
편향    →  안 간 길이 있다고 알려준다   →  ★ 앵커링 탈출
```

**③이 이 도메인의 존재 이유다.**
①②는 토론용 코산도 한다. ③은 `axis` 가 있어야만 된다.

> **앵커링은 없앨 수 없다. 그러나 주소를 갖게 만들 수는 있다.**
> 보이면 사람이 고칠 수 있다.

## STOP: Q1 ★ 이 문서의 핵심

**메타 Q1:** "이 도메인에서 결정이란 무엇인가? → 함수가 된다."

**이 질문은 답이 없다.**

### 왜 없는가

```
소설    인물이 원칙을 버린다        →  결정.  fn.
토론    논자가 주장을 철회한다      →  결정.  fn.
생각    ???
```

생각에서 뭔가를 "결정"하면 — **그 순간 생각이 끝난다.**

```
"A다"라고 결정   →  그 뒤는 A를 정교화하는 것.  탐색이 끝났다.
"A일까?"로 열기  →  이게 생각이다.  그런데 이건 결정이 아니다.
```

**메타는 결정을 함수로 만들라고 한다. 그런데 생각의 본체는 결정이 아니라 열기다.**

### 결정만 담으면 무슨 일이 벌어지나

억지로 답해봤다:

```
fn think(problem) {
    clash   가설A >< 가설B
    branch  근거1 => 가설A  ! 가설B 폐기
            근거2 => 가설B  ! 가설A 폐기
    Δ       belief = A
}
```

**이건 토론이다.** 그리고 **답이 이미 두 개로 정해져 있다.**
가설 A와 B가 어디서 왔는지는 아무 데도 안 적혀 있다.
**진짜 생각은 A와 B를 만드는 데 있었는데, 그 부분이 통째로 코산 밖에 있다.**

> **메타 Q1로 만들면, 생각의 결말만 코드가 되고 생각 자체는 산문으로 남는다.**

이것이 이 도메인의 STOP이다.

## 발견: 메타에 원시 개념이 하나 없다 ★

메타 Q1~Q8은 전부 **수렴** 쪽 질문이다.

```
Q1  결정      → 고른다
Q2  지속       → 유지한다
Q3  도망       → 막는다
Q4  모름       → 표시한다
Q5  무너짐     → 부순다
Q6  좋음       → 통과시킨다
Q7  굴리기     → 진행한다
Q8  key/text  → 가른다
```

**"연다"에 해당하는 질문이 없다.**

그럴 만하다 — 소설과 토론은 **씨앗이 주어진 상태에서 시작**한다.
인물이 있고, 주제가 있다. 코산은 그것을 굴려서 무너뜨린다.

**그런데 생각은 씨앗을 만드는 일이 절반이다.**
무엇을 물을지, 어떻게 자를지, 어느 축으로 볼지 — 그걸 정하는 게 생각이다.
그리고 메타에는 그 자리가 없다.

### 그래서 Q0 을 제안한다

```
Q0. 이 도메인에서 "연다"는 무엇인가?
    → 발산 장치가 된다.
    - 무엇이 갈래를 만드는가.
    - 갈래는 무엇에서 나오는가.  (무에서 나오면 그건 창작이다)
    - 언제 그만 열고 닫는가.
```

**소설/토론에서는 이 질문이 사소하다.** (사건을 지어낸다 / 공격을 찾는다)
**생각에서는 이게 본체다.**

→ 메타에 Q0을 추가하되, **도메인마다 무게가 다르다**는 것도 적어야 한다.

## 우회하지 않고 다시 세운다 — `open` 을 1급 시민으로

STOP을 인정하고, **결정이 아니라 열기를 중심**으로 다시 짠다.

### 대전제 (수정)

```
깊은 생각 = 물음이 갈라지고, 갈라진 것이 서로를 무는 연쇄
결정      = 그 연쇄가 더 이상 갈라지지 않을 때 자동으로 남는 것.  ★ 목표가 아니라 잔여물.
```

**결정을 하지 않는다. 갈래가 죽으면 남은 게 답이다.**

이렇게 하면 fn 이 결정을 내리지 않아도 된다. **갈래를 죽이기만 하면 된다.**

## Q0. "연다"는 무엇인가 → `open` ★ 이 도메인의 본체

```
open O_<n> {
    from     <what>            ★ 무엇에서 나왔나.  무에서 나오면 창작이다.
    axis     <n>               ★ 어느 축으로 갈랐나.  ← 이게 핵심
    forks    [ F1, F2, ... ]   갈래들.  2개 이상.
    text     "..."             한 문장.  이 물음이 무엇인가.
    steps    int               ★ v0.2.  이 축에서 굴린 스텝 수.  자동 집계.
                                 0 이면 장식이다.  여는 건 발산이 아니다.
    ?? rel   "..."             ★ v0.3.  갈래들의 관계.  안 굴렸으면 ?? 로.
                                 비워두면 렌더링이 채운다. (§렌더링 규율)
    leaves   [ ?? ... ]        다음이 물 고리
}
```

### `axis` 가 이 도메인의 핵심이다 ★

**갈래는 축이 있어야 나온다.** 축이 없으면 그냥 나열이다.

```
✗  forks = [ 가능성A, 가능성B, 가능성C ]
      → 어디서 나왔나?  왜 셋인가?  AI가 그럴듯한 걸 세 개 뽑은 것.  = 평균.

✓  open O1 {
       from   = 문제.전제
       axis   = 시간_규모                    ← ★ 축을 이름으로 못 박는다
       forks  = [ 단기_참, 장기_참 ]
       text   = "이게 언제 참인가"
   }
   open O2 {
       from   = 문제.전제
       axis   = 행위자                       ← ★ 다른 축
       forks  = [ 개인_수준, 집단_수준 ]
       text   = "누구에게 참인가"
   }
```

**같은 것에서 다른 축으로 열면 다른 갈래가 나온다.**
그리고 **축을 이름으로 적어야만 "다른 축이 또 있나?"를 물을 수 있다.**

> **산문은 축을 안 적는다. 그래서 첫 축에 갇힌다.**
> 이것이 앵커링의 정체다. 축이 하나만 열리고, 그게 안 보인다.

### 축을 다 열었는지 검사한다 ★

```
□ 같은 from 에서 열린 open 이 2개 이상인가     → 축이 하나면 앵커링이다
□ 각 axis 가 서로 다른 이름인가                → 같은 축을 두 번 열면 가짜 발산
□ ?? axis 가 남아 있는가                       → 아직 못 찾은 축.  자원.
```

**이것이 다양성을 기계적으로 강제하는 방법이다.**

### 갈래는 무에서 못 나온다

```
✓  from = 문제.전제           전제를 뒤집어서
✓  from = O3.F2               앞 갈래를 다시 갈라서
✓  from = counterexample(E1)  반례에서
✓  from = clash(A, B)         모순에서
✗  from = ??                  ← 그냥 떠올랐다.  창작.  반려.
```

**갈래는 무언가에서 자란다. 뽑아내는 게 아니라 자라는 것이다.**

## Q1. 결정이란 무엇인가 → `kill` (fn 이 아니다) ★

**결정하지 않는다. 갈래를 죽인다.**

```
kill K_<n>(<fork>) {
    when    <state_condition>
    ground  <근거>                      ★ 무엇이 이 갈래를 죽이나
    type    contradiction | counterexample | subsumed | irrelevant
    proc    <n> -> <n> -> <n>           ★ 이름으로.  문장 금지.
    Δ       <fork>.status = dead
    !       <cost>                      ★ 죽이면 잃는 것
}
```

### 갈래를 죽이는 네 가지 방법

```
contradiction    다른 확정된 것과 모순된다
counterexample   반례가 있다                        ★ 가장 강하다
subsumed         다른 갈래에 포함된다.  독립적이지 않았다.
irrelevant       문제와 무관하다.  ★ 축을 잘못 잡은 것이다 → open 을 고쳐라
```

**`irrelevant` 가 나오면 그건 갈래의 버그가 아니라 축의 버그다.**
→ open 으로 되돌아가서 axis 를 고친다. ★ 이게 왕복이다.

### 죽이는 데도 대가가 있다 ★

```
!  그 갈래가 물고 있던 leaves 가 전부 끊긴다
!  그 갈래에 의존하던 다른 open 들이 재검사된다
```

**공짜로 못 죽인다.** 그래야 "그럴듯하지 않아서 버렸다"가 안 된다.

```
✗  kill  { ground = 직관,  type = ?? }        ← 근거 없이 죽임.  최악.
✗  kill  { ground = "설득력이 없다" }          ← 인상.  반려.
✓  kill  { ground = F3,  type = counterexample }
```

**죽음은 사실에서만 온다. 인상으로 죽이면 그게 평균이다.**

class question {

class fork {

    from     <open_id>

## Q3. AI는 어떻게 도망가는가 → 연산자 ★ 가장 중요

**이 도메인의 도망은 소설·토론과 또 다르다.** 깊이 있는 척한다.

| 도망 | 연산자 | 강제되는 것 |
|---|---|---|
| **첫 축으로 끝까지 간다** | `axis` 필수 + 축 개수 검사 | ★ 최대의 도망.  아래 참조 |
| **축을 열어놓고 안 굴린다** | `steps` 집계 | ★★ v0.2 신규.  아래 참조 |
| 갈래를 그럴듯하게 뽑아냄 | `from` 필수 | 무엇에서 나왔는지 대라 |
| "여러 관점이 있다" 하고 나열 | `axis` 필수 | 축을 대라.  나열은 발산이 아니다 |
| "결국 중요한 것은" | **금지** | 합치지 마라.  합치는 게 평균이다 |
| "깊이 들여다보면" | 칸 없음 | 무엇이 갈라지는지 적어라 |
| 인상으로 갈래 버리기 | `kill.ground` 필수 | 근거 없는 kill 은 STOP |
| "~일 수도 있다" | `??` | 모르면 모른다고 적어라 |
| 결론 먼저 내고 논증 붙이기 | `from` 추적 | ★ 갈래가 어디서 나왔는지 역추적된다 |
| 무한히 파고들기 | `depth` 제한 | 아래 참조 |
| 예쁜 문장 | 칸 없음 | 렌더링에서 붙인다 |

### 첫 축으로 끝까지 가는 것 ★ 이 도메인의 최대 도망

산문 사고에서 AI는 이렇게 도망간다:

```
문제 제시
   ↓
첫 관점을 잡는다        ← 여기서 축이 정해진다.  그런데 안 적는다.
   ↓
그 관점을 깊이 판다      ← 깊어 보인다.  실제로 깊다.
   ↓
결론                    ← 다른 축은 존재한 적도 없다
```

**깊이는 진짜다. 그런데 축이 하나다.**
그리고 축이 안 적혀 있으므로 **하나라는 것조차 안 보인다.**

**구조로 막는다:**

```
open 은 반드시 axis 를 적는다
   → 같은 from 에서 axis 가 하나뿐이면 검출된다
   → field.?? axis 에 "아직 안 열린 축"을 강제로 등록시킨다
   → 그게 남아 있는 한 PASS 못 한다
```

**다양성이 규율이 아니라 구조로 강제된다.**

### 축을 열어놓고 안 굴린다 ★★ v0.2 — 위보다 더 교활하다

첫 축 도망을 막으면, AI는 **한 단계 위에서 도망친다.**

```
축을 세 개 연다        ← 검사를 통과한다.  "다양하게 봤습니다"
   ↓
한 축만 굴린다         ← ★ 여기서 도망친다
   ↓
나머지 축은 열린 채 방치
   ↓
결론                  ← 결국 한 축의 결론이다
```

**열었다는 사실이 알리바이가 된다.** 그리고 v0.1 PASS 는 이걸 통과시켰다.

**`open` 은 값싸다.** 축은 얼마든지 열 수 있다. 그러니 여는 것을 세면 안 된다.
**굴리는 것을 세야 한다.**

```
open O2 {
    axis   = 중독의_출처
    forks  = [ F4, F5, F6 ]
    steps  = 0                    ★ 굴린 스텝 수.  자동 집계.
}
```

```
□ 모든 open 의 steps > 0 인가                    → 0 이면 장식이다
□ 한 axis 가 전체 steps 의 과반을 먹지 않았는가    → 먹으면 앵커링
```

**여는 것은 발산이 아니다. 굴리는 것이 발산이다.**

### 무한 후퇴 ★

전제의 전제의 전제를 물으면 끝이 없다. (토론용 코산에서도 이게 열린 문제였다)

```
depth   현재 깊이
??      어디서 멈추나
```

**임시 규칙:** `kill` 이나 `answered` 를 못 내는 깊이에 도달하면 STOP.
**멈추는 게 성과다.** 그 자리가 이 문제의 바닥이다.

```
&        동시에 참인 둘
><       양립 불가
->       함의
=>       선택
??       구멍 / 안 열린 축         ★ 채우면 최악의 위반
?!       모르지만 사실은 정해짐     ★ 자원
!        대가 (되돌릴 수 없다)
X        갈래 파기
⊢ / ⊬    지지한다 / 안 한다
axis     가르는 축                ★ 이 도메인 고유
from     어디서 나왔나             ★ 이 도메인 고유
fork     갈래
kill     갈래를 죽인다             ★ fn 을 대체
```

## Q5. "무너진다"는 무엇인가 → `collapse`

```
collapse C<n> {
    trigger   reveal(F*) | counterexample(E*)
    check     premise.val == false
    effect    <fork>* X  ->  status = dead        ★ 여러 갈래가 한꺼번에 죽는다
    cascade   depends_on(premise) 전부 재검사
    reopen    <axis>                              ★ 무너지면 다시 열어야 한다
    cost      죽은 갈래의 leaves 전부 끊김
}
```

**소설/토론과 다른 점: 무너지면 다시 열린다.** ★

```
소설    원칙이 무너진다  →  새 원칙으로 교체     (수렴)
토론    주장이 죽는다    →  cascade             (수렴)
생각    전제가 무너진다  →  ★ 그 위의 갈래가 다 죽고, 축을 다시 열어야 한다  (발산)
```

**무너짐이 발산을 낳는다.** 이게 이 도메인의 왕복이다.

```
step 7   premise P2.val = false  (반례 발견)
         → fork F1, F3, F4 전부 dead  (P2에 의존)
         → ⚠ O1.axis 가 P2 를 전제하고 있었다
         → STOP: axis_invalidated
         → ★ open O1 을 다시 짜야 한다.  다른 축으로.
```

**축이 무효화되는 것이 최대의 성과다.** 갇혀 있던 데서 나오는 유일한 길이다.

## Q6. "좋다"는 무엇인가 → 통과 조건

**사람이 쓴다. 결과가 아니라 과정에 건다.**

**세 층으로 검사한다.** (v0.2 — **편향은 노드 검사로 원리적으로 안 잡히기 때문**)

### ① 노드 검사 — 개별 요소가 규율을 지켰나

```
□ 모든 fork 에 from 이 있는가                     무에서 나온 갈래 = 창작
□ 모든 kill 에 ground 가 있는가                   인상으로 죽이면 반려
□ 모든 open 에 axis 가 이름으로 있는가            축 없는 갈래 = 나열
□ premise.hidden 이 전부 드러났는가               숨은 전제가 남으면 헛생각
□ premise 가 ?? 구간을 거쳤는가                   한 방에 뒤집히면 공짜
□ 모든 leaves 가 언젠가 hooks 되었는가            미회수 = 버려진 고리
```

### ② 집계 검사 — 분포가 기울지 않았나 ★★ v0.2 신규 · 편향 검출

```
□ 같은 from 에서 axis 가 2개 이상 열렸는가        하나면 앵커링
□ ★ 모든 open 의 steps > 0 인가                  열고 안 굴리면 장식이다
□ ★ 한 axis 가 전체 steps 의 과반을 먹지 않았는가  먹으면 앵커링
□ ★ 죽은 fork 가 한 axis 에 몰려 있지 않은가      한 축만 검증한 것
□ field.?? axis 가 비었는가                       못 연 축이 남으면 미완
```

**실제로 실패한 판:**

```
   O1(차별화_대상)   steps = 8   ← 전체의 80%.  ★ 과반 초과.  FAIL.
   O2(중독의_출처)   steps = 0   ← ★ 열어놓고 방치.  장식.  FAIL.
   O3(실패_모드)     steps = 2

   개별 위반: 0개.  모든 노드가 규율을 지켰다.
   그런데 이 판은 앵커링이다.
```

> **편향은 잘못한 것이 아니라, 잘한 것들의 분포다.**
> 그래서 세어야만 잡힌다.

### ③ 결과 검사

```
□ 최소 1개 fork 가 kill 되었는가                  아무도 안 죽으면 생각을 안 한 것
□ 최소 1개 axis 가 무효화되었는가 (collapse)      안 되면 첫 축 안에서만 논 것
□ 결론이 하나로 합쳐지지 않았는가            ★ 합쳐졌으면 평균화가 일어났다
□ 축 독립성:  축 순서를 바꿔 굴려도 살아남는 fork 가 같은가
   달라지면  → 앵커링이다.  축이 결과를 결정했다.       ★ 기계 검출
```

### 통과 조건은 코산 안에 있다 ★ v0.2

**v0.1은 통과 조건을 코산 밖에 뒀다. 틀렸다.**
나중에 확정하면 **앞의 kill 들이 소급 무효화된다.**

```
step  set_pass { text = "내가 만들고 싶은 재미" }
      cascade  모든 kill.ground 를 PASS 기준으로 재검사
               → K1.ground = "시장에서 다 망했다"
               → ⚠ 시장 근거.  PASS(재미) 와 무관.
               → K1 무효.  F1.status = ?? 로 복구.
```

**통과 조건 확정도 하나의 스텝이고, 파괴력이 가장 크다.**
늦게 정할수록 많이 무너진다. **그래도 몰래 가정하는 것보다 낫다.**

### 축 독립성 검사 ★ 이 도메인 고유

```
소설    여러 번 굴려 결과가 같으면    → 나쁘다 (평균)
토론    순서를 바꿔 결과가 달라지면   → 나쁘다 (앵커링)
생각    축 순서를 바꿔 살아남는 갈래가 달라지면 → 나쁘다 (앵커링)
```

**세 도메인이 전부 "여러 번 굴려 비교"하는데, 무엇이 나쁜지가 다 다르다.**
→ 메타 10절은 이걸 도메인 질문으로 내려야 한다. (토론용 §발견 2에서 이미 나왔다)

## 앵커링 탈출 ★★ v0.5 — steps 개수가 아니다

**v0.4 는 "한 축이 steps 과반이면 앵커링"으로 기계 판정하려 했다. 그건 보조 신호일 뿐이다.**

진짜 앵커링 탈출은 이렇게 일어난다:

```
사람:  "이 축으로 생각하면 어떻게 돼?"        ← ★ 사람이 새 축을 던진다
코산:  그 축을 open 으로 열어 굴린다
       → 기존 축 옆에 나란히 쌓는다 (버리지 않는다)
사람:  "A 축에선 이게 결론인데 B 축에선 다르네" → ★ A 가 앵커였구나
       "그럼 C 축은?"                          → 계속 던진다
```

**개수를 세는 게 아니라, 다른 축을 실제로 굴려서 결과가 달라지는지 본다.**
그리고 그 축은 **사람이 던진다.** (§사람이 하는 일)

### 왜 산문은 이걸 못 하나 ★★ 핵심

산문에게 "이 축으로 생각해봐"라고 물으면 **답은 한다. 그런데 그 답도 앵커링에 걸린다.**

```
산문에게 "B 축으로 생각해"
   → B 로 시작하지만, 그 새 줄기도 첫 토큰이 방향을 잡고 또 쏠린다
   → ★ 질문을 바꿔도 앵커링 구조 자체는 안 바뀐다.  다른 앵커로 갈아탈 뿐.
```

더 나쁜 건, **산문은 이전 축을 못 버린다.** 이전 문장이 전부 컨텍스트에 살아 있으니까.

```
새 방향을 물으면 산문은 둘 중 하나를 한다:
   ① 거부:  "이전이 낫다" 며 이전 앵커를 방어한다
   ② 오염:  새 방향에 이전 이야기를 섞는다.  ★ 반대 방향인데도.
   → 갈아타는 게 아니라 이전 위에 덧칠한다.
```

### 코산은 방향이 함수라 안 섞인다 ★★

```
open A_축 { ... }        A 방향.  독립된 구조.
open B_축 { ... }        B 방향.  ★ A 를 from 으로 참조 안 하면 A 가 안 낀다.
```

**함수가 다르면 이전 게 낄 자리가 없다.**
산문은 **순서**가 곧 영향이다 (먼저 쓴 게 위에 남아 누른다).
코산은 **참조**가 영향이다 (물어봐야 낀다). 안 물으면 안 낀다.

그래서 반대 방향을 **진짜 반대로** 굴릴 수 있다. 이전을 안 물면 되니까.

### 격리에는 층이 있다

```
산문 한 세션        A 전문(全文)이 컨텍스트에 살아있음  →  강한 오염 (거부/섞임)
코산 한 세션        A 는 파일로 닫힘, 세션엔 흔적만      →  약한 영향
코산 다른 세션      A 를 아예 모름                       →  완전 독립
```

**세션 기억만큼은 영향이 남는다. 그러나 산문보다 훨씬 약하다** — 산문은 A 전문이
눌러앉지만, 코산은 A 가 파일로 압축돼 흔적만 남기 때문이다.
완전 독립이 필요하면 **세션을 갈라라** (§렌더링 규율 4-1 과 같은 원리).

> **산문의 앵커링 = 순서. 먼저 쓴 게 자동으로 누른다. 못 버린다.**
> **코산의 격리 = 참조. 물어본 것만 낀다. 안 물면 독립이다.**
> 순서를 참조로 바꾼 것 — 이것이 코산이 앵커링에 강한 이유다.

### steps 분포는 보조 신호다

```
□ 한 axis 가 전체 steps 의 과반을 먹지 않았는가
   → 먹었으면 "쏠렸을 수 있다" 는 ★ 힌트.  자동 판정 아님.
   → 진짜 확인은:  다른 축을 굴려 결과가 달라지나? (위)
   → 그리고 "다른 축을 굴릴지" 는 사람이 정한다.
```

## Q7. "굴린다"는 무엇인가 → 시뮬레이션

**한 스텝 = 한 open 또는 한 kill.** 시간 단위가 아니다.

```
1. state.now 확인 (물음/갈래 그래프)
2. when 조건 맞는 open / kill 탐색
3. 없으면   → STOP: nothing_fires
             ★ 열 것도 죽일 것도 없다 = 생각이 끝났거나, 축을 못 찾은 것
   여럿이면 → 갈라진다.  각각 굴린다.
4. open:  axis 등록 + forks 생성 + field.?? axis 갱신
   kill:  ground -> type -> proc -> Δ -> cost
5. ground 없는 kill → STOP: unfounded_kill
6. from 없는 fork → STOP: fork_from_nothing            ★ 창작 방지
7. collapse trigger 검사 → 발동하면 갈래 몰살 + axis 재검사 + reopen
8. 반복
```

### 시뮬레이터에게 ★

**너는 생각하지 않는다. 코산에 없으면 STOP 한다.**

**실제로 겪은 위반 (v0.1 굴리기 중):** ★

- **축을 세 개 열고 한 축만 굴렸다.** 개별 위반은 0개였고, PASS 를 통과했다.
  "다양하게 봤습니다"라는 알리바이가 생겼다. → **이게 이 도메인의 최악이다.**
  → v0.2 집계 검사가 여기서 나왔다.
- 통과 조건 없이 갈래를 죽였다. 시장 근거로 죽였는데, 통과 조건은 재미였다.
  → **기준 없이 죽이면 자기 기준으로 죽인다.** 그게 평균이다.

**예상되는 위반:**
- 갈래를 **지어낸다.** `from` 없이. "그럴듯해서" 넣는다. → **창작이다.**
- 축을 안 적고 갈래만 낸다. → 다음에 다른 축을 못 찾는다.
- 못 죽이는 갈래를 **인상으로 죽인다.** "설득력이 없어서". → 평균화.
- 끝에 **"종합하면"으로 합친다.** → 발산을 다 하고 마지막에 평균 냄.

**멈추는 게 성과다.**

### 검사자는 없다 — 다만 계수기는 있다 ★ v0.2

**노드 위반은 굴리기가 잡는다:**
- 갈래를 지어내면 → `from` 이 비어서 STOP.
- 인상으로 죽이면 → `ground` 가 비어서 STOP.
- 합치면 → PASS 실패.

**그런데 편향은 굴리기가 못 잡는다.** 굴러가긴 하니까.
**세어야 잡힌다.**

```
open.steps      각 축이 소모한 스텝 수.  자동 집계.
                ★ 이것만은 굴리기 밖에서 세야 한다
```

**금지하지 않는다. 불가능하게 만든다. 다만 기울어진 것은 세야 보인다.**

## 렌더링 규율 ★★ v0.3 신규 — 실제로 새서 추가한 것

**코산을 산문(글)으로 렌더링할 때, 렌더링 AI가 `??` 자리를 그럴듯하게 메꾼다.**

실제 사고:
```
논문 → [코산 분석] → O5.cosan → [렌더링] → 산문

O5.cosan:
   forks = [ F15, F16 ]
   steps = 2
   (F15 와 F16 의 관계가 없다 — 두 갈래를 열었지만 둘 사이는 안 굴렸다)

렌더링 산문:
   "개발 초기에는 F15 가 작동하고, 콘텐츠가 쌓이면 F16 이 발동한다"
   → ★ 소스에 없는 시간 순서를 지어냄
```

**렌더링 AI는 O5.cosan 만 받았다.** 논문도, 분석 대화도 못 받았다.
그런데 순서가 나타났다 → **렌더링이 빈자리를 메꾼 것이다.**

### 왜 메꿨나 — 규율이 없어서

**메타 3절: 금지하지 않는다, 불가능하게 만든다.**
렌더링에 그 관문이 없었다. 그래서 AI의 기본값(그럴듯하게 채우기)이 나왔다.

### 규율 1. 코산에 없는 것은 렌더링에도 없다

```
렌더링은 빌드다.  소스에 없는 인과 · 순서 · 관계를 만들지 마라.
   ✗  from / Δ / ground 에 없는 인과를 문장으로 지어낸다
   ✗  forks 사이의 관계가 코산에 없는데 "A 다음 B" 라고 쓴다
   ✓  코산에 있는 것만 살로 붙인다.  없으면 안 쓴다.
```

### 규율 2. `??` 는 `??` 로 렌더링한다 ★

```
렌더링이 ?? 를 만나면:
   ✗  그럴듯하게 채운다
   ✓  "이 부분은 밝혀지지 않았다" / "여기는 미결" 로 렌더링한다
   → ?? 는 결함이 아니라 사실이다.  "모른다" 가 사실이면 "모른다" 로 쓴다.
```

### 규율 3. 암묵적 공백을 명시적 `??` 로 만들어라 ★★ 진짜 원인

**빈자리가 두 종류다. 렌더링은 이 둘을 구별 못 한다.**

```
명시적 빈자리   ?? rel        → 렌더링이 "밝혀지지 않음" 이라 쓴다
암묵적 빈자리   (그냥 없음)     → ★ 렌더링이 "없나 보다" 하고 채운다
```

O5 는 **암묵적**이었다 — `forks` 만 있고 관계는 언급조차 없었다.
그래서 렌더링이 "안 밝혀진 것"과 "원래 없는 것"을 구별 못 하고 채웠다.

```
✗  open O5 { forks = [F15, F16],  steps = 2 }
                                          ← 관계가 암묵적으로 비어 있다

✓  open O5 {
       forks = [F15, F16]
       steps = 2
       ?? rel   "F15 와 F16 의 공존 방식 — 순서인가 동시인가"   ← 명시적 구멍
   }
   → 렌더링이 ?? rel 을 만나 "둘의 관계는 밝혀지지 않았다" 로 쓴다.  못 채운다.
```

**갈래를 둘 이상 열었으면, 갈래 사이의 관계도 `??` 로 명시하라.**
관계를 안 굴렸으면 그 자리가 `?? rel` 이다. 비워두면 렌더링이 채운다.

### 검사 추가

```
□ forks 가 2개 이상인 open 에 관계 정보 또는 ?? rel 이 있는가
   → 없으면 암묵적 공백.  렌더링이 채운다.  ★ 위반.
□ 렌더링 산출물에 코산의 from/Δ/ground 로 추적 안 되는 인과가 있는가
   → 있으면 렌더링이 지어낸 것.
```

### 규율 4. 렌더링은 참조망만 본다 ★★ v0.4 — 가장 근본적인 누수

v0.3 렌더링이 이렇게 썼다:
```
depends [F1] 뿐인데  →  "게임의 규칙 틀이 먼저 확립되어야 성장 시스템이 성립한다"
```

F5.cosan 에도, F1.cosan 에도 "먼저 · 확립 · 성립 · 순서" 가 없다.
**그 "먼저" 는 참조망 밖에서 새어 들었다** — 자동 로드된 메모리, 또는 게임 상식.

```
렌더링이 보는 것:
   ✓  대상 노드 (F5)
   ✓  그 참조망 (from / depends / leaves 로 연결된 것 = O2, F1, O5)
   ✗  메모리 · 자동 로드 문서 · 프로젝트 배경          ← 근거로 쓰지 마라
   ✗  훈련된 도메인 상식 (게임이 어떻게 돌아가는지)      ← 근거로 쓰지 마라
```

**근거는 반드시 참조망 안에서 나와야 한다.**
참조망에 없으면, 그 문장은 코산이 아니라 AI가 아는 것이다. 빼라.

### 규율 4-1. 구조적 격리 — 안 보여주는 게 확실하다 ★

**"보지 마라" 는 약하다. 컨텍스트에 있으면 조건이 된다.**

```
✗  메모리가 자동 로드된 세션에서 렌더링       → 새어 든다
✓  렌더링 세션은 메모리를 로드하지 않는다
   또는 참조망 파일만 명시적으로 준다
   → ★ 못 보게 하면 못 쓴다.  권한이 규율이다.
```

채팅용 코산의 "def/ 만 보여준다" 와 같은 원리다.

### 규율 5. 관계를 시간 순서로 바꾸지 마라 ★ v0.4

```
depends / from / ->  는 의존이지 순서가 아니다.
   ✗  "정의한다"  →  "먼저 정의돼야 한다"     시제·양상 변환
   ✗  "F1 에 의존" →  "F1 다음에 온다"        의존 → 순서
   ✓  "F1 에 의존한다" / "F1 과 관계있다"      까지만
```

**의존에는 여러 종류가 있다** (논리적 / 시간적 / 정의적).
코산이 어느 것인지 안 밝혔으면, 렌더링이 하나로 찍지 마라.
찍고 싶으면 소스에 `?? dep_kind` 가 있어야 한다.

### 이것이 코산의 강점을 보여준 사례 ★

**세 AI가 각자 다른 세션이었다.** (논문 작성 / 코산 분석 / 렌더링)
산문으로 넘겼다면 "논문에서 봤나 렌더링이 지어냈나" 가 영원히 안 갈렸을 것이다.

**코산이라 O5.cosan 한 파일만 대조하면 끝났다.**
파일이 좁은 통로라서, 무엇이 안 넘어갔는지가 보인다.
**범인을 몰라도 "소스에 없다" 가 잡힌다.**

## 코산이 하는 일 / 사람이 하는 일 ★ v0.5

**코산은 찾아서 채우지 않는다. 보이게 한다.**

```
코산이 한다 (보이게)      사람이 한다 (정한다)
─────────────────────    ─────────────────────
쏠린 곳을 드러낸다        더 팔지 정한다
  (steps 분포, 축 대조)      ("이 축으로 생각하면?")
빈 곳을 드러낸다          빈 데 갈지 정한다
  (?? axis, ground 없음)     ("여기 파줘")
갈래를 나란히 쌓는다      새 축 열지 정한다
  (버리지 않고 대조)          ("반대로 생각하면?")
```

**기존 AI 는 산문으로 답해서 빈틈이 안 보였다.** 물어봐도 자기 산문을 보고
쏠림·빈 곳을 못 찾았다. 안 쓴 건 구조로 안 남으니까.
**코산은 그걸 구조로 남긴다.** 그래서 사람이 보고 고를 수 있다.

**셋(더 팔지 / 빈 데 갈지 / 새 축 열지)은 전부 사람이 정한다.**
이건 가치 판단이다. 통과 조건을 사람이 쓰는 것과 같은 층이다.
**AI 가 자동으로 정하려 들면, 그건 평균이 나오거나 자동화 앵커에 걸린 것이다.**

## 사람이 하는 일

```
1. 씨앗       문제 (한 문장이면 된다)
2. 통과조건    무엇이 좋은 생각인가          ← 이건 넘기지 않는다
3. 요청       "다른 축으로 열어봐"          ← ★ 이 도메인에서 가장 많이 할 요청
4. 판단       AI가 연 축을 보고 고친다      ← ★ 틀린 축을 보면 맞는 축이 떠오른다
5. 판 고르기   여러 trace 중에서           ← ★ 평균 탈출은 여기서
```

**결론을 요구하지 마라** — 요구하는 순간 평균이 나온다.
**축 목록과 살아남은 갈래를 요구하라.**

## 요청 처리

```
① 열기 요청        "다른 축으로 열어봐"
                   → field.?? axis 에서 하나 꺼낸다
                   → 없으면 STOP: "이 문제에서 더 열 축을 못 찾겠습니다"
                   → ★ AI가 "네"라고 안 한다

② 죽이기 요청      "F3 죽여봐"
                   → ground 를 찾는다.  못 찾으면 STOP.
                   → ★ "그럴듯하지 않아서" 는 ground 가 아니다

③ 상태 지정        "이 문제가 어디서 갈리는지 보여줘"
                   → axes 목록을 낸다.  결론은 안 낸다.
```

## 발견 — 세 번째 도메인이 메타에 대해 알려준 것 ★

### 발견 1. 메타에 Q0(연다)이 없다 — 확인됨

소설·토론은 씨앗이 주어진다. 생각은 씨앗을 만드는 게 절반이다.
**메타 Q1~Q8은 전부 수렴 질문이다.**

→ **메타에 Q0 추가:**
```
Q0. 이 도메인에서 "연다"는 무엇인가?  → 발산 장치
    - 무엇이 갈래를 만드는가
    - 갈래는 무엇에서 나오는가 (무에서 나오면 창작)
    - 도메인마다 무게가 다르다.  생각에서는 이게 본체다.
```

### 발견 2. `fn` 이 도메인 특수였다 ★

메타는 "결정 → 함수"를 골격으로 놓는다. 그런데 이 도메인에서는 **결정이 목표가 아니다.**
`fn` 대신 `kill` 을 썼고, 그게 더 정확했다.

**결정은 잔여물이다. 갈래를 다 죽이면 남는 것.**

→ 메타 Q1을 이렇게 고쳐야 한다:
```
✗  Q1. 이 도메인에서 "결정"이란 무엇인가?
✓  Q1. 이 도메인에서 상태를 바꾸는 것은 무엇인가?
       (결정일 수도, 배제일 수도, 다른 것일 수도 있다)
```

### 발견 3. `??` 를 쪼개야 한다 ★

```
?? value   값을 모른다   → 수렴 작업
?? axis    축을 모른다   → 발산 작업        ★ 전혀 다른 작업이다
```

메타는 `??` 를 하나로 둔다. 그러면 **발산해야 할 때 AI가 수렴한다.**

→ 메타 Q4 확장: "이 도메인에서 '모른다'가 몇 종류인가?"

### 발견 4. 무너짐의 방향이 도메인마다 다르다

```
소설    무너지면  →  새 원칙으로 교체       (수렴)
토론    무너지면  →  cascade 로 전파        (수렴)
생각    무너지면  →  ★ 축을 다시 연다       (발산)
```

메타 Q5는 "무너진 다음"을 안 묻는다. 물어야 한다.

### 발견 5. 메타 3절이 반쪽이었다 ★★ v0.2 — 실증됨

**메타 3절:** "금지하지 않는다. 불가능하게 만든다."

**틀리진 않았는데, 못 막는 게 있다.**

굴려봤더니 **모든 노드가 규율을 지켰는데 전체가 기울었다.**
구조로 막을 수 있는 건 **개별 요소의 위반**이다.
**분포의 기울어짐은 구조가 못 막는다.** 하나하나가 다 합법이니까.

```
불가능하게 만든다   →  개별 위반을 막는다     (빈틈, 창작)
세어서 보이게 한다  →  ★ 분포를 드러낸다      (편향)
```

→ **메타에 추가해야 한다:**
```
3절 보강:
  금지하지 않는다      →  불가능하게 만든다
  불가능하게 못 하면   →  ★ 세어서 보이게 만든다
  
  구조로 막을 수 없는 것이 있다.  분포가 그렇다.
  그때는 막지 말고 집계하라.  보이면 사람이 고친다.
```

**이것이 앵커링에 대한 답이다.**
앵커링은 위반이 아니다. 그래서 못 막는다.
**그러나 셀 수는 있다. 그리고 세려면 축이 이름을 가져야 한다.**

### 발견 6. 세 도메인의 "여러 번 굴리기" 판정이 전부 다르다 — 확정

```
소설    결과가 같으면    → 나쁘다 (평균)
토론    순서 바꿔 다르면  → 나쁘다 (앵커링)
생각    축 바꿔 다르면    → 나쁘다 (앵커링)
```

메타 10절의 "다 같으면 가짜 분기"는 **소설의 기준**이다. 반드시 도메인으로 내려야 한다.

## 실증 — v0.1로 한 판 굴린 기록 ★ v0.2 신규

**문제:** "뱀서라이크는 어떻게 차별화하는가"
**통과 조건:** "내가 만들고 싶은 재미" (굴리는 도중에 확정 → 소급 무효화 발생)

### 작동한 것

```
✓  씨앗 전제가 죽었다
   P0("차별화가 필요하다") → val = false
   근거: 플레이어는 차별화를 안 원한다.  뱀서라이크를 찾는 사람은 뱀서를 또 하고 싶다.
   → 차별화의 수요자는 개발자였다.
   → ★ 문제 자체가 무효화됨.  problem_v2 로 재정의.

✓  통과 조건이 앞을 소급 무효화했다
   PASS = 재미  →  K1.ground = 시장  →  무관  →  K1 무효

✓  무너짐이 재개방을 낳았다
   collapse → axis 무효 → reopen        (§Q5 에서 예측한 대로)

✓  빈틈이 주소를 갖고 남았다
   ground 없는 F3,  회수 안 된 F5/F13,  ?? 로 남은 P1
```

**산문으로 했으면 "차별화 방법 10가지"가 나왔을 자리에서, 문제가 죽었다.**

### 실패한 것 ★ 이게 v0.2를 낳았다

```
✗  시뮬레이터(AI)가 앵커링에 걸렸다

   O1(차별화_대상)   steps 8   ← 문제 문장에 있던 단어.  첫 축.
   O2(중독의_출처)   steps 0   ← 열어놓고 방치
   O3(실패_모드)     steps 2

   → "차별화"라는 첫 축에서 끝까지 못 나왔다.
   → 차별화를 부정하는 결론까지 냈는데, 그것도 차별화 좌표계 위에서 나온 것이다.
   → ★ 개별 위반 0개.  v0.1 PASS 통과.

✗  "뱀서의 재미가 뭔가"를 한 번도 안 물었다
   통과 조건이 "재미"인데 재미의 정의가 없다.
   → 나머지 전부가 판정 불가 상태였다.
   → O2 를 굴렸으면 나왔을 것이다.  열어놓고 안 굴려서 안 나왔다.
```

**결론: v0.1은 앵커링을 검출하지 못했다. 그래서 v0.2에 집계 검사를 넣었다.**

### 그리고 이 판이 방법 자체를 증명했다 ★

**시뮬레이터가 앵커링에 걸렸다는 사실이 코산에 남아 있었다.**

```
산문이었다면    O2 는 존재한 적도 없다.  안 판 축을 물어볼 대상이 없다.
코산이었으므로  O2 가 파일에 있었고,  steps = 0 이 세어졌고,  편향이 보였다.
```

> **앵커링은 없앨 수 없다. AI도, 사람도.**
> **그러나 축이 이름을 가지면, 앵커링에 주소가 생긴다.**
> **주소가 있으면 고칠 수 있다.**

**이 코산은 자기가 못 막은 것을 자기가 드러냈다.** 그게 이 방법이 작동한다는 증거다.
